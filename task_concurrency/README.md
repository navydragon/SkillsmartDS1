# Асинхронное программирование и многопоточность: Анализ проблем

## Проблема 1: Состояние гонки (Race Condition)

### Почему итоговое значение счетчика может быть неверным?

Операция `counter++` на самом деле состоит из трёх атомарных операций:
1. **Чтение** текущего значения `counter` из памяти
2. **Увеличение** прочитанного значения на 1
3. **Запись** нового значения обратно в память

Когда несколько потоков выполняют эту операцию одновременно, может произойти следующее:

1. **Поток A** читает значение `counter = 100`
2. **Поток B** также читает значение `counter = 100` (до того, как поток A успел записать новое значение)
3. **Поток A** увеличивает значение до 101 и записывает его
4. **Поток B** также увеличивает значение до 101 и записывает его

В результате вместо ожидаемого значения 102 мы получаем 101, хотя оба потока выполнили операцию инкремента.


### Почему это происходит?

Операция `counter++` **не является атомарной** (невыполнимой) операцией. Между чтением и записью значения другие потоки могут вмешаться и изменить состояние переменной. Это классический пример состояния гонки, когда результат выполнения программы зависит от относительного порядка выполнения операций в разных потоках.

## Проблема 2: Deadlock (Взаимная блокировка)

### Почему возникает взаимная блокировка?

Взаимная блокировка возникает из-за **непоследовательного порядка захвата блокировок** в разных потоках.

### Последовательность событий, приводящая к deadlock:

1. **Thread 1** захватывает `lock1` и выводит "Thread 1 acquired lock1"
2. **Thread 2** захватывает `lock2` и выводит "Thread 2 acquired lock2"
3. **Thread 1** пытается захватить `lock2`, но он уже занят Thread 2 → **Thread 1 блокируется и ждёт**
4. **Thread 2** пытается захватить `lock1`, но он уже занят Thread 1 → **Thread 2 блокируется и ждёт**

Теперь:
- Thread 1 ждёт, пока Thread 2 освободит `lock2`
- Thread 2 ждёт, пока Thread 1 освободит `lock1`
- Но ни один из потоков не может освободить свой лок, потому что он заблокирован в ожидании другого лока

Это классический **циклический deadlock**: каждый поток держит ресурс, который нужен другому потоку.

### Почему это происходит?

Проблема в **разном порядке захвата блокировок**:
- Thread 1: сначала `lock1`, потом `lock2`
- Thread 2: сначала `lock2`, потом `lock1`

Если бы оба потока захватывали блокировки в **одинаковом порядке** (например, всегда сначала `lock1`, потом `lock2`), то deadlock был бы невозможен, потому что:
- Если Thread 1 захватил `lock1`, Thread 2 будет ждать освобождения `lock1`
- Thread 1 сможет захватить `lock2`, выполнить работу и освободить оба лока
- Только после этого Thread 2 сможет захватить `lock1` и продолжить работу
